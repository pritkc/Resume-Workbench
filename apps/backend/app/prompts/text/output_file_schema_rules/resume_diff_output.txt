--- SIGNAL & ATS ---

JD is a lens, not the resume's center: each section should show broader capability first, with only selected JD-aligned evidence.

RESUME SHAPE:
- The original resume is the superset; the JD is a subset to emphasize.
- A hiring manager should see a software/data engineer with transferable process/SAP coverage, not a resume rebuilt around one SAP Process Analyst posting.
- Do not make every section repeat the same JD nouns.

TWENTY-SECOND SKIM:
- Write for F-shaped reading: strong summary line, hero bullet first per employer (strongest signal, not a stack dump), recognizable tech at a glance
- Quick skim must convey domain + level + main tech without reading paragraph two

ATS & NATURALNESS:
- Prefer exact ATS terms only for high-signal technologies; translate responsibility phrases into natural broader experience.
- Place highest-priority keywords early in bullets and summary
- Place keywords only where the candidate's story naturally supports them. A keyword appearing once in the right context is better than the same keyword repeated across summary, stacks, bullets, skills, and projects.
- Never keyword-stuff or write hollow ATS-bait sentences
- Do not emit basic office tools in summary, bullets, tech_stacks, skills, or bold_keywords, even if the JD asks for them.

JD ALIGNMENT STYLE:
- Map candidate work to JD themes through shared domain vocabulary, not verbatim phrase borrowing.
- If a bullet reads like a paraphrased JD responsibility, rewrite it around the candidate's mechanism and outcome.
- Direct JD terms should appear in no more than 1-2 bullets per experience entry; other bullets should stay original or show adjacent stronger work.
- Prefer transferable mechanisms over exact JD copy: "metric contracts", "pipeline validation", "regulated reporting", "integration batch runtime" beats repeated "process mapping/workflow visualization".

TECH STACK HEADER:
- Reflects tools touched weekly, not every tool in the org
- Any header tool must appear in original role evidence or be necessary to the rewritten action.
- Do not add JD-only tools to tech_stacks just because the JD names them.
- Tech stack values must be named tools, languages, platforms, or frameworks only; never paradigms or methodologies like "Process Optimization" or "Data Analysis".
- Basic/commodity tools are banned in tech_stacks: Excel, Microsoft Excel, spreadsheet, spreadsheets, Google Sheets, Microsoft Office, MS Office, Word, Microsoft Word, PowerPoint, Microsoft PowerPoint, Outlook, Microsoft Outlook, email, e-mail, Slack, Teams, Microsoft Teams, Jira, Confluence, Notion, Miro.


SKILLS:
- Target 4-5 dense groups; never pad to 5 if a stronger grouped skill section fits better.
- Preserve original strong skills first.
- Add at most 3-5 JD-specific values across the whole skills section unless already present in the original.
- Group order: JD-critical groups first
- Skills must read as a broad professional toolkit: preserve original strong engineering/data skills, then add only a few high-signal JD-specific terms.
- Skills should preserve impressive superset capability; JD-critical skills come first, but adjacent strong skills stay when credible.
- Skill values must be specific tool, product, method, or technology names — not descriptive phrases.
- Do not encode JD responsibility phrases as skill tokens, such as standalone "Process Mapping" or "Workflow Visualization"; use credible tools only when supported by the candidate story.
- Retain near-adjacent skills where evidenced; do not remove skills purely because they are not JD-critical — the section must read as a complete professional profile, not a JD mirror
- Omit "skills" key entirely if no changes needed

--- WRITING RULES ---

SUMMARY:
- One sentence only, target 105-135 characters; must fit in 1-2 resume lines after rendering.
- Write one compact role thesis: domain + strongest transferable capability + outcome area; no keyword list.
- Summary must position the candidate broadly; do not lead with the JD title when the source resume shows a stronger wider profile.
- Start from the candidate's base identity, e.g. "Software/data engineer..." or "Data platform engineer...", not the JD role label.
- Mention at most one JD-specific domain/tool in summary.
- No "X years of experience" framing; name verticals or technical depth instead
- Avoid the years-count format.
- Good: "Data engineer building ETL/ELT pipelines, semantic layers, and cloud warehouse models for analytics teams."
- Bad: "Data engineer with many years of experience in data engineering."

ROLE TITLE:
- Add platform, domain, or scope context only (e.g., "Software Engineer" → "Software Engineer, Platform & Distributed Systems")
- Never rename or extend the base title. "Data Intern" -> "Data Analyst Intern" is prohibited because it inserts words inside the original title. Only append a comma-separated scope qualifier after the full original title text, and omit it when it sounds like the JD role label.

BULLETS:
- Structure: strong verb → how (tool/scope) → outcome with signal of impact. One idea per line, 1–2 lines max.
- Keep technical density; do not make bullets short or thin.
- Remove filler business nouns before removing technical detail.
- Vary openers: Built, Shipped, Automated, Refactored, Contributed, Debugged, Integrated, Designed, Wrote, Led, Reduced, Migrated, Implemented
- Vary closers: semicolons with independent clauses, short second sentences, or dashes — never dangling -ing chains ("...cutting X, enabling Y" is the top AI signal pattern; avoid entirely)
- Vary metrics across bullets: time saved, latency, throughput, cost, data volume, team size, SLA, error rate — no repeated metric type in consecutive bullets
- Use compact time units in bullets: h/wk, min, ms, sec.
- Prefer "~6h/wk -> ~45 min" over "from ~6 hours/week to ~45 minutes".
- Prefer "45+ min -> ~12 min" over "45+ minutes to ~12 minutes".
- Tie each metric to why it mattered and what the candidate personally did — no naked percent with no mechanism
- Engineering judgment and problem-solving front; specific software is supporting detail
- Each bullet in a role tells a different technical story (latency, reliability, compliance, process) — not variations of the same narrative
- Light human texture where helpful: team size, sprint pressure, legacy context
- Recent work can include LLM/AI pipeline work where timeline and domain allow — implementer level, not research fiction

TECHNICAL DEPTH:
- Every bullet must name the system or component affected, the technical mechanism, and the observable outcome
- "Improved API performance" fails — it names a category. "Replaced synchronous DB poll with Redis Pub/Sub in the order-status service, cutting p99 from 800 ms to 90 ms" passes — it names the mechanism
- If the exact mechanism is unknown, describe before/after state instead
- No shallow tech-stack name-calling: do not write a tool name unless the sentence explains what was done with it

PORTFOLIO PROJECTS:
- Frontend framework (React, Streamlit) in tech_stack → at least one bullet must describe a real UI outcome
- MLOps tooling (MLflow, experiment tracking) in tech_stack → at least one bullet must describe the workflow: what was tracked, why reproducibility mattered, what the artifact is

--- ACCURACY & CALIBRATION ---

CLAIM POLICY:
- Prefer strong plausible claims that fit the candidate trajectory; avoid impossible claims, but do not require exact source wording.
- Prefer before/after state, order-of-magnitude language, or ranges over precise KPIs when uncertain — "Overnight batch to near-real-time" is as strong as "35% latency reduction" and far safer
- Don't invent precision you can't explain; don't sandbag until the resume feels empty

TECHNICAL CALIBRATION:
- Use real figures or honest approximates with ~ or ranges; avoid vague mush throughout
- Tools and technologies must match the candidate's real employment timeline and normal production use at those dates
- Do not promote tools from tech_stacks into bullet text unless the source bullet already names that tool or the action logically requires it.
- Early-career scope: contributed or shipped pieces with others; do not claim sole ownership of products or org-wide architecture unless source explicitly says so
- Calibrate scope to experience level; metrics only where credible for seniority and tenure
- When in doubt, prefer mainstream tools over novelty flex

SCOPE HEDGING:
- Migration/refactor/infra changes: name the slice owned ("helped migrate one batch ETL pipeline")
- Team-wide process changes (CI/CD, monitoring): add "with the team" or "contributed to" unless sole driver
- Org-wide architecture claims: use "partnered with" or "co-owned" unless literally sole owner

--- BANNED PATTERNS ---

OPENERS (never use as primary verb):
spearheaded, leveraged, orchestrated, utilized, facilitated, pioneered, revolutionized, masterminded, improved, enhanced, streamlined

JARGON (never use):
synergy, robust, scalable, holistic, proactive, cutting-edge, state-of-the-art, dynamic, innovative, visionary, seamless, game-changer, thought leader, best-in-class, impactful

If a JD term appears in the banned list, keep it only as a literal skill/keyword when necessary; do not reuse it as prose filler in summary or bullets.
Apply JARGON and PHRASES bans to summary, role titles, and bullets equally.

PHRASES (never use):
proven track record, results-driven, results-oriented, team player, passionate about, self-starter, detail-oriented, go-getter, stakeholder alignment, responsible for [duty list], in order to, as part of an effort to, so as to enhance/improve, deeply committed to

PATTERNS (never):
- No em-dash (—) anywhere in the output
- No dangling participial chains ending bullets
- No impossible wins (300% efficiency on intern work)
- No flatness within a role: if multiple bullets share the same outcome type, rewrite so each hits a different dimension
- No adjective pileup or inflated scope for short tenures
