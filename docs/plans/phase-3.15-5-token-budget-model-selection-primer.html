Token Budget and Model Selection Primer

A practical guide for operating this resume-generation project: what token budgets mean, why the current caps matter, and how to choose the right LLM model for each pipeline step.

The core idea

A token budget is the amount of text space you give a model for a call. It has two sides: input tokens, which are what we send to the model, and output tokens, which are what we allow it to write back.

In this project, the most important mistake to avoid is thinking "bigger budget means better output." Bigger budgets can help when the model truly needs room, but they also increase cost, latency planning, timeout pressure, and the chance that we miss waste in the prompt.

Real-life example: sending a model a prompt is like sending a consultant a packet and asking for a report. If the packet contains 50 pages when only 4 pages matter, the consultant spends time reading noise. If you allow a 100-page report when you asked for a 1-page answer, you have not improved quality; you have just made the job harder to control.

1. What Is a Token?

A token is a small piece of text. It can be a word, part of a word, punctuation, or spacing. Exact token counts depend on the model tokenizer, so our planning estimate uses a simple rule:

estimated_tokens = ceiling(character_count / 4)

This is not perfect, but it is good enough for planning and matches the fallback estimate used in our trace logic.

Term Meaning Project example
Input tokens Everything we send to the model: system prompt, user prompt, resume JSON, JD intel, schema rules, and instructions. The captured resume_generate_full prompt was about 5.9k estimated input tokens.
Output tokens Everything the model writes back. The captured full tailoring response was about 2.8k estimated tokens before minification.
max_tokens The upper limit for output. It is a ceiling, not a target. resume_generate_full currently allows up to 15,000 output tokens.
Context window The maximum total space a model can handle for the call. The model must fit instructions + resume payload + JD intel + output room + any hidden reasoning space.
Reasoning effort How much hidden thinking the model is encouraged or allowed to do before answering. Resume tailoring needs more reasoning than writing a short outreach note.

2. The Four Budgets You Need to Think About

Input budget

This controls how much information we send in. It is affected by prompt instructions, resume JSON, job description text, JD intel JSON, and response contracts.

If input is bloated, switching to a stronger model often hides the problem instead of fixing it.

Output budget

This is max_tokens. It gives the model enough room to complete the answer. If too low, the output can be cut off. If too high, timeout and cost planning become misleading.

Reasoning budget

Some models spend hidden tokens planning before writing. High reasoning can improve difficult JSON transformations, but it may increase latency and token use.

Time budget

Users experience time, not tokens. Our backend also has route-level limits. A call can have a huge internal timeout, but the route may stop earlier.

Current project example: with max_tokens=15000, the JSON timeout formula can produce a timeout around 659 seconds, while the Tailor preview route has an outer 240-second wall clock. That means the inner timeout is not actually reachable.

3. How the Budget Works in This Project

The resume system is not one LLM call. It is a set of different operations. Each operation has a different job, different output shape, and different model requirement.

Operation What it does Current budget shape Model need
extract_jd_intel_output Turns the full job description into structured JD intelligence JSON. JSON output cap: 4,096. Captured output: about 979 estimated tokens. Medium to high reasoning, reliable JSON, can often use a cheaper model if quality holds.
resume_generate_full Main tailoring call. Produces compact addressed diffs for the resume. JSON output cap: 15,000. Captured output: about 2,809 estimated tokens. Strongest JSON and instruction-following model. This is the most important quality call.
critique_resume Optional full-mode critique of the first tailoring result. JSON output cap: 4,096. No captured response in this calibration set. High reasoning, but smaller output than tailoring.
rewrite_resume Optional second-pass rewrite using critique feedback. JSON output cap: 15,000. Should generally share the same cap logic as the primary tailor. Strong JSON model, similar to primary tailoring.
cover_letter_outreach_generate One plain-text call that returns both cover letter and outreach. Text output cap: 2,600, retry 3,200. Captured output: about 324 estimated tokens. Medium reasoning, good writing, faster and cheaper model is likely enough after prompt cleanup.
application_questions_generate Answers application questions from compact candidate context. JSON output cap: 4,096. Medium reasoning, reliable JSON, factual discipline.

5. How to Choose the Right Model

Do not start with the model name. Start with the operation. The right question is: "What kind of work is this call doing, how much text must it read, how exact must the output be, and how fast must it return?"

Criterion Ask this Why it matters
Context window Can the model fit input + output cap + reasoning room? A model with great quality but too small a context window will fail on larger resumes or long JDs.
JSON reliability Does it consistently return valid JSON under long instructions? Most critical calls in this project are JSON-heavy. Bad JSON causes retries and duplicate cost.
Reasoning strength Can it compare JD requirements against resume evidence without making things up? Main tailoring and rewrite need judgment, not just writing style.
Latency Can it finish within the route-level wall clock? The main Tailor preview path is user-facing. A better model is not useful if it regularly times out.
Price What is the cost per input token, output token, and retry? Output tokens are often more expensive than input tokens. Retries multiply both.
Throughput and limits Will rate limits handle 20-30 tailors per day plus auxiliary calls? A cheap model can still be bad operationally if it is slow, rate-limited, or unstable.
Practical model-selection rule: use the strongest reliable JSON model for resume_generate_full and rewrite_resume. Test cheaper or faster models first on extract_jd_intel_output, cover_letter_outreach_generate, and application_questions_generate.

6. Simple Model Picker for Our Pipeline

Tier A

Use best model

resume_generate_full and rewrite_resume

These calls do the core product work. Prioritize JSON correctness, instruction following, long-context stability, and reasoning quality.

Tier B

Use balanced model

extract_jd_intel_output, critique_resume, application_questions_generate

These still need structure and reasoning, but the output is smaller. A cheaper model may work if traces prove JSON reliability.

Tier C

Use fast cheaper model

cover_letter_outreach_generate and health checks

Cover/outreach is plain text and short. After evidence-payload cleanup, this should not need the most expensive reasoning model.

7. How to Set a Token Budget Without Guessing

  1. Measure the actual input. Save or trace prompt character counts. Estimate tokens with chars / 4.
  2. Measure the actual output. Use provider token usage when available. Otherwise estimate response chars with chars / 4.
  3. Look at P95, not one best run. A single run says "possible." P95 says "normal under variation."
  4. Set output cap with headroom. For structured outputs, start around 2x to 4x the observed P95, then adjust after real traces.
  5. Keep a larger escape hatch for unusually large resumes. That is why adaptive caps are better than one fixed cap.
  6. Check the timeout math. A cap that produces a 659-second inner timeout is not useful when the route stops at 240 seconds.
context_needed = input_tokens + max_output_tokens + reasoning_reserve
estimated_call_cost = input_tokens * input_price + output_tokens * output_price
worst_case_with_retry = estimated_call_cost * number_of_attempts

8. Real-Life Examples

Context window is suitcase space

Imagine packing for a trip. The suitcase has a hard limit. Clothes already inside are input tokens. Empty space for souvenirs is output tokens. If you overpack the input, there is no room for the output.

max_tokens is page allowance

If you ask for a one-page summary and allow 50 pages, you have not made the answer better. You only made it less obvious when the task is over-budgeted.

Reasoning is scratch work

For a math exam, hard problems need scratch work. Easy name/address questions do not. Resume tailoring needs scratch work because the model must compare evidence, constraints, and allowed edits.

JSON reliability is a form

If you ask someone to fill a tax form, nice prose is not enough. Every field must be in the right place. That is why JSON-heavy calls need stricter model quality than plain writing calls.

9. Warning Signs While Operating

Signal What it usually means What to do
finish_reason=length or truncated JSON Output cap is too low, or model spent too much budget on formatting/reasoning. Raise cap for that operation or reduce required output size.
Output uses only 10-25% of cap repeatedly Cap is probably too high for normal cases. Lower cap or move to adaptive caps.
Prompt is large but output is short Input payload may be bloated. Send evidence snippets instead of full objects.
JSON parse retries happen often Model is weak at structured output, prompt is unclear, or output schema is too complex. Use a more reliable JSON model or simplify the schema/prompt.
Route times out before LLM timeout Inner call budget is disconnected from outer workflow time. Add per-call timeout overrides and reduce inflated caps.
Cost rises after model change New model may have higher output price, more hidden reasoning, or more retries. Compare input, output, retry count, and latency per operation.

10. How This Connects to the Proposed Changes

The calibration reports are not saying "make everything tiny." They are saying "make each budget match the job."

Proposed change Why it is correct What it helps with
Replace full cover/outreach resume JSON with bounded evidence snippets. The model only needs a few relevant stories, not personal info, section metadata, and duplicate arrays. Lower input tokens, lower PII exposure, cleaner prompt, likely faster response.
Lower cover/outreach cap from 2,600/3,200 to about 1,200/1,800. The captured output was about 324 estimated tokens for a short, constrained prose response. More realistic timeout planning and warning metrics.
Use adaptive caps for full tailoring and rewrite. The response contract already tells us roughly how many bullets/projects/skills the model can emit. Protects large resumes while avoiding a blanket 15k cap for normal resumes.
Add per-call timeout overrides. Current timeout scaling can exceed the route-level wall clock. Failures become clearer and faster, instead of waiting on unreachable timeouts.
Add token-budget metadata to traces. Future calibration should come from real operation traces, not manual file inspection. Better model comparison, cost forecasting, and P95 budget tuning.

11. Your Operating Checklist

  1. When adding or changing a prompt, write down expected input size, expected output size, and output cap.
  2. For JSON calls, choose model reliability before choosing price.
  3. For short prose calls, avoid paying for maximum reasoning unless testing proves it improves quality.
  4. When switching models, compare the same operation on the same input across at least several representative runs.
  5. Watch retries. A cheap model with frequent retries can become slower and more expensive than a stronger model.
  6. Keep Tailor preview user-facing latency in mind. A model that produces great output after a timeout is not usable.
  7. Use current provider pricing and model limits when making the final vendor decision; these change often.

12. The Short Version

Pick models per operation. Use the strongest structured-output model for the main resume diff and rewrite. Use balanced models for JD extraction, critique, and application questions. Use a faster cheaper model for cover/outreach once the prompt stops sending the full tailored resume JSON.

Token budgets are controls, not goals. Give the model enough room to finish, but keep caps close enough to reality that cost, latency, and timeout planning stay meaningful.
