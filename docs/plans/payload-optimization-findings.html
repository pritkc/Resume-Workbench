High · Token waste F1 — Extracted JD JSON is immediately re-listed as labeled text directly below itself

In resume_generate_full/prompt.txt, the full JD intel JSON is embedded at one line. The very next block manually re-extracts five fields from that same JSON as labeled human-readable lines: Rewrite angles, ATS keyword list, Bold keyword source, Domain/product terms, Level ceiling. The model already has the full object; the labeled restatement adds no instruction, just characters.

Redundant block (lines 38–42)
  Rewrite angles (one per role...): [
    "analyze and support business processes...",
    "perform data analysis...", ...
  ]
  ATS keyword list (translation...):
    ["SAP","Power BI","Miro","process mapping",...]
  Bold keyword source (short...):
    ["SAP","Power BI","Miro","Process Mapping",...]
  Domain/product terms (weave...):
    ["Global Trade Operations","supply chain",...]
  Level ceiling (do not exceed...):
    "Individual contributor who analyzes..."
Already in the JSON above (line 36)
"responsibility_themes": [...],
"resume_technical_keywords": [
  "SAP","Power BI","Miro","Excel",
  "process mapping", ...
],
"resume_bold_keyword_sources": [...],
"resume_domain_keywords": [...],
"calibration": {
  "level_expectations": "..."
}
Side-effect bug: The manual ATS list drops "Excel" that exists in the JSON's resume_technical_keywords. Duplication creates silent field-level divergence between what the model sees in the JSON vs. the labeled lists.

Fix: Delete lines 38–42 entirely. The model reads directly from the JSON. The labeled block adds no constraint beyond what the schema rules already express.
Estimated saving: ~200 tokens per run, zero risk.

High · Prompt quality F2 — Tool exclusion in extract_jd_intel is a hardcoded name list, not a role-aware principle

The resume_bold_keyword_sources rule in the extract prompt reads: 

Exclude...basic/table-stakes tools such as Excel, Google Sheets,
Microsoft Office, Word, PowerPoint, Outlook, email, Slack, and Jira.

This is a frozen list of named tools. It cannot reason about the role's level or domain — it can only match literals. A better instruction tells the model why certain tools are excluded, so it can apply the same judgment to any tool in any JD without needing the list to be updated.

Evidence this approach fails: The model still surfaced JIRA in both bold_keywords and the Skills section of the response, justifying it as "a key defect tracking tool." The named list was present but did not prevent the inclusion — because the model rationalized around it using the JD context.

The resume_generate_full prompt already uses a better, universal form on line 109: 

Do not emit basic office tools in summary, bullets, tech_stacks,
skills, or bold_keywords, even if the JD asks for them.

But even that lacks role calibration. The right principle is: a tool belongs in bold keywords only if a recruiter scanning resumes for this role level would find it noteworthy — not assumed baseline. Whether a tool clears that bar depends on the role domain, not on whether it appears in a static exclusion list.

Fix: Replace the named-tool exclusion list in extract_jd_intel with a role-aware reasoning rule, for example: 

Exclude any tool that would be assumed baseline for someone at this
role's level and domain. Ask: would a recruiter scanning this role's
resumes consider this tool a differentiator, or an expected minimum?
If expected minimum → exclude, regardless of whether the JD names it.

Apply the same framing to the parallel instruction in resume_generate_full (line 109) so both prompts reason consistently.
Token saving: minimal (list length ≈ named rule length). Value is in correctness and maintainability — no list to update as tools evolve.

Medium · Token waste F3 — RESPONSE CONTRACT repeats company and project names already in ORIGINAL RESUME JSON

The RESPONSE CONTRACT block at the end of the prompt includes: 

"experience": {
  "entries": ["Humana (Contract)","SDSU CSRC","GoFundMe","Sudathi"],
  "bullet_counts": [5,2,3,3]
},
"projects": {
  "entries": ["ClaimSight","FundFlow","LogLens"],
  "bullet_counts": [1,1,1]
}

These names and counts are fully derivable from ORIGINAL RESUME JSON, which is already in the same prompt. The index mapping note — "key '0' = entries[0]" — is sufficient to establish the numbering scheme without listing the names again.

Fix: Remove entries and bullet_counts from the RESPONSE CONTRACT. Keep only the index note and the mode/output_keys fields.
Estimated saving: ~25–30 tokens per run, zero risk.

Low · Token waste F4 — Extract JD prompt states "Output JSON only" twice in four consecutive lines

The system message for extract_jd_intel opens with: 

You extract JD facts into JSON for resume tailoring. Output JSON only (no prose/markdown).
Stay anchored to the JD; do not invent. Missing → null for scalars, [] for arrays.

You must respond with valid JSON only. No explanations, no markdown.

Lines 1 and 4 convey the same constraint with no additional nuance. The repetition does not reinforce compliance — it just adds tokens.

Fix: Remove line 4. The constraint is already in line 1.
Estimated saving: ~15 tokens per run.

Low · Output quality F5 — scale_signals filled with qualitative environment phrases when the JD contains no actual scale data

The extract prompt's schema example shows quantitative signals: "1M+ daily transactions", "multi-region deployment". But for this JD — which contains no scale figures — the model returned: 

"scale_signals": ["global trade operations", "fast-paced, regulated environment"]

These are qualitative environment labels, not scale indicators. When scale_signals flows into the resume prompt as context, vague filler is worse than an empty array because the model may try to "demonstrate scale" using phrases that have no grounding in the candidate's actual work.

Fix: Add one rule to the extract prompt: 

scale_signals: emit [] when the JD contains no quantitative or
scope signals. Do not populate with qualitative environment descriptors
("fast-paced", "regulated") — those belong in company_context.

No token saving — this is a correctness fix.
